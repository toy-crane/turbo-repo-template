# 모바일 인증

## 결정

- Supabase Auth를 앱 인증 세션의 기준으로 사용한다.
- iOS는 Apple, Google, 이메일 인증 코드를 지원한다. Android는 Google과 이메일 인증 코드를 지원한다.
- Google과 Apple은 네이티브 로그인이 발급한 ID Token을 `signInWithIdToken`으로 Supabase에 전달한다. 브라우저 OAuth 콜백은 사용하지 않는다.
- Google 로그인은 `react-native-nitro-google-signin`을 사용한다. Apple 로그인은 `expo-apple-authentication`을 사용한다.
- 로그인 버튼은 제공자의 공식 버튼 컴포넌트 대신 앱이 직접 그린다. Google, Apple, 이메일 버튼은 같은 모양과 폭을 쓰고, 채움과 테두리 색만 각 제공자의 브랜드 규칙을 따른다.
- 로그인은 방법 선택, 이메일 주소, 인증 코드의 세 화면으로 나눈다. 이메일과 인증 코드 화면은 네이티브 Stack의 뒤로가기를 사용한다.
- 이메일 인증 코드는 여섯 자리가 채워지면 바로 확인한다. 코드 다시 받기는 전송 대기 시간이 끝난 뒤에만 실행한다.
- 제공자 로그인마다 새 nonce를 만든다. 제공자에는 SHA-256 해시를 전달하고 Supabase에는 원본을 전달한다. nonce 검사를 끄지 않는다.
- 유효한 Supabase 세션은 앱 시작 때 복원한다. 세션이 없을 때만 새 로그인을 시작하며, 로그인 전에는 보호 화면을 열 수 없다.
- iOS에서 새 Google 로그인이 필요하면 계정 선택 화면을 명시적으로 연다. 저장된 Google 자격 정보만으로 새 Supabase 로그인을 백그라운드에서 만들지 않는다.
- 이메일은 6자리 인증 코드만 지원한다. 로그인과 가입은 하나의 흐름이며 magic link, 비밀번호와 비밀번호 재설정은 제공하지 않는다.
- 같은 확인 이메일을 가진 신원은 Supabase의 안전한 자동 연결에 맡긴다. 앱은 신원 수동 연결이나 사용자 병합 기능을 만들지 않는다.
- 일반 로그아웃은 현재 기기의 Supabase 세션과 Google SDK의 로컬 로그인 상태, 사용자별 Query 캐시만 지운다. 제공자 동의 철회나 다른 기기 세션 종료는 하지 않는다.
- 로컬 이메일 로그인은 로컬 Mailpit에서 최신 인증 코드를 읽는 저장소 명령과 `agent-device`를 표준 화면 검증 경로로 사용한다.
- `public.profiles`는 `auth.users`와 일대일로 연결한다. 데이터베이스가 인증 사용자와 함께 프로필 행을 만들고 지운다. 로그인한 사용자는 다른 사용자의 공개 프로필을 읽을 수 있지만 자기 행만 수정할 수 있다. 클라이언트는 프로필 행을 만들거나 지우지 않는다.
- 제공자가 준 이름과 이미지는 빈 프로필 값만 채운다. 사용자가 저장한 값을 제공자 정보로 덮어쓰지 않는다.
- 각 프로젝트는 Google, Apple과 Supabase 자격 정보를 새로 만든다. 템플릿은 실제 자격 정보나 다른 프로젝트의 값을 포함하지 않는다.

## 경계

- 앱은 iOS와 Android만 지원한다. 웹 로그인은 범위에 포함하지 않는다.
- Android에서는 Apple 로그인을 제공하지 않는다.
- Google 로그인은 기본 신원 정보와 ID Token만 요청한다. Google API 추가 권한, access token, offline access와 `serverAuthCode`를 사용하지 않는다.
- 직접 그린 버튼은 각 제공자가 허용한 문구, 로고 자산, 색상 조합만 쓴다. Google은 "Continue with Google"의 현지화와 지정 색을, Apple은 허용된 세 문구와 검정 또는 흰색 배경을 지킨다. 로고를 다시 그리거나 색을 바꾸지 않는다.
- 일반 로그아웃은 `supabase.auth.signOut({ scope: "local" })`을 사용한다. 전체 기기 로그아웃과 다른 기기만 로그아웃하는 기능은 별도 제품 기능이다.
- 설정 화면 로그아웃 버튼의 진행 표시는 [모바일 작업 진행 표시](mobile-action-progress.md)를 따른다. 진행 중에도 문구는 `로그아웃` 그대로 둔다.
- Google 로그아웃에는 로컬 `signOut`을 사용한다. `revokeAccess`는 계정 연결 해제 기능을 따로 만들 때만 사용한다.
- Apple은 별도 제공자 로그아웃을 호출하지 않는다. 앱 세션과 Supabase 세션만 지운다.
- 로컬 이메일 도구는 로컬 Supabase와 Mailpit에서만 동작해야 한다. 원격 URL, 관리자 API, `service_role`, 고정 세션과 토큰 출력을 허용하지 않는다.
- 계정 삭제의 사용자 흐름과 삭제 범위는 [모바일 계정 삭제](mobile-account-deletion.md)를
  따르고, 서버 권한과 삭제 순서는
  [계정 삭제 서버 경계](account-deletion-server-boundary.md)를 따른다.

## 이유

네이티브 제공자 로그인은 iOS와 Android의 표준 계정 선택 UI를 유지하면서 Expo Development Build 안에서 동작한다. Supabase는 제공자가 발급한 ID Token을 검증하고 앱 세션을 발급하므로 앱이 별도 인증 서버를 만들 필요가 없다. nonce는 로그인 요청과 반환된 ID Token을 한 번의 시도에 묶어 재사용 공격을 막는다. Supabase 세션을 기준으로 삼으면 제공자 캐시가 남아 있어도 앱의 로그인 여부를 하나의 상태로 판단할 수 있다. 로그인 단계를 화면별로 나누면 각 화면이 한 가지 입력과 오류만 다루고 네이티브 뒤로가기로 이전 값을 고칠 수 있다.

현재 기기만 로그아웃하면 한 기기에서 나간 동작이 다른 기기의 작업을 갑자기 끊지 않는다. 제공자 동의도 유지하므로 다음 로그인 때 불필요한 재동의를 요구하지 않는다. 로컬 이메일 인증 코드는 실제 Supabase Auth 경로를 그대로 사용하면서 외부 메일과 운영 비밀 없이 에이전트가 화면을 검증할 수 있다. 프로필 행의 생명주기와 소유권을 데이터베이스가 맡으면 클라이언트가 사용자 관계를 바꾸지 못한다. 제공자 값으로 빈 칸만 채우면 사용자가 고친 프로필도 보존된다.

## 재검토 조건

- 웹 앱을 제품 범위에 추가해 브라우저 OAuth와 딥 링크 콜백이 필요할 때
- Google 또는 Apple이 공식 버튼 컴포넌트의 폭 제약을 없애거나 브랜드 규칙을 바꿀 때
- Android에서 Apple 로그인을 지원해야 할 명확한 제품 요구가 생길 때
- Google API 데이터나 서버 장기 접근 권한이 필요할 때
- 계정 병합 요청이 반복되어 자동 신원 연결만으로 사용자를 지원하기 어려울 때
- 보안 정책상 로그아웃 때 모든 기기 세션이나 제공자 동의를 함께 철회해야 할 때
- CI에서 실제 제공자 로그인을 반복 실행할 전용 계정과 기기 환경을 운영할 때

## 계속 제외하는 대안

- Google과 Apple을 브라우저 OAuth로 통일: 네이티브 계정 선택 UI를 잃고 딥 링크, 콜백과 Apple 웹 자격 정보 관리가 추가된다.
- 저장된 Google 자격 정보로 새 Supabase 로그인을 자동 생성: 사용자가 계정을 확인할 기회가 없으며 로그아웃 뒤에도 다시 로그인된 것처럼 보일 수 있다.
- 제공자의 공식 버튼 컴포넌트를 그대로 사용: Google의 공식 버튼은 폭이 고정이라 화면 폭에 맞출 수 없다. 실측에서 Google 190pt, Apple 342pt로 두 버튼의 짝이 맞지 않았고, 다크 모드에서는 공식 Google 버튼이 브랜드 규칙에 없는 모양으로 그려졌다. 대신 브랜드 규칙, 현지화, 접근성 이름을 앱이 직접 지킨다.
- 이메일 magic link: 로컬 화면 검증에 외부 링크 처리와 딥 링크가 필요해진다.
- 관리자 API로 테스트 사용자를 만들거나 세션을 주입: 실제 이메일 인증 화면과 RLS 경로를 검증하지 못하고 서버 전용 비밀이 테스트 도구로 퍼진다.
- 로그아웃 때 제공자 접근 권한 철회: 일반 로그아웃보다 훨씬 큰 동작이며 다음 로그인에 재동의를 요구한다.

## 보존할 근거

- HeroUI Native `InputOTP`의 `pasteTransformer`는 운영체제가 입력 길이만큼 자른 뒤의 값만 받는다. 코드 외 글자가 섞인 긴 문자열에서는 앞 여섯 글자 안의 숫자만 채울 수 있다. 여섯 칸 입력을 직접 만들기 전에는 이 한계를 없앨 수 없다.
