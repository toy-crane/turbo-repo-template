# 검토 에이전트 실행 경계

## 결정

- 구현 대화와 분리해야 하는 검토는 Claude Code와 Codex의 전용 agent로 실행한다.
- 도구가 함께 써야 하는 검토 기준은 `.agents/reviewers/<name>.md`에 한 번만 둔다.
- `.claude/agents/<name>.md`와 `.codex/agents/<name>.toml`은 각 도구의 agent 이름, 설명, 모델, 읽기 전용 권한과 공용 검토 계약 경로만 연결한다.
- 검토 계약을 `.agents/skills`나 `.claude/skills`에 두지 않는다. 구현 세션이 같은 맥락에서 reviewer 작업을 직접 실행할 수 있는 경로를 만들지 않는다.
- 구현 에이전트는 검토 에이전트에 기준 ref와 검토 범위만 전달한다. 구현 과정의 판단이나 기대하는 결론은 전달하지 않는다.

## 경계

- 검토 에이전트는 저장소 지침, 결정 계약, 적용 중인 명세, 변경 diff와 테스트 증거를 읽는다. 프로젝트 근거를 공유하는 것은 구현 대화 기록을 공유하는 것으로 보지 않는다.
- Supabase나 Postgres 지식처럼 검토 기준과 별개로 여러 작업이 쓰는 분야 지식은 Skill로 유지하고 검토 에이전트에 미리 넣을 수 있다.
- 커밋, 배포, 설계 정리처럼 현재 대화에서 실행하는 공용 작업은 기존 `.agents/skills` 원본과 `.claude/skills` 연결 방식을 유지한다.
- 검토 에이전트는 finding을 고치지 않는다. 수정과 재검토는 호출한 구현 에이전트가 별도 단계로 진행한다.

## 이유

Skill은 현재 구현 대화에서도 직접 실행할 수 있으므로 그 자체로 별도 검토 맥락이나 읽기 전용 권한을 만들지 않는다. 검토 기준까지 플랫폼별 agent 파일에 복사하면 두 도구의 판정 기준이 달라질 수 있다. 공용 검토 계약과 얇은 플랫폼별 agent 설정을 나누면 판정 기준은 같게 유지하면서 대화 맥락과 권한은 분리할 수 있다.

## 재검토 조건

- Claude Code와 Codex가 같은 agent 정의 형식과 같은 권한 경계를 직접 지원할 때
- 어느 한 도구가 전용 agent에서 저장소의 공용 검토 계약을 읽을 수 없게 될 때
- 별도 agent로 실행해도 구현 대화의 판단이 반복해서 검토 결과에 섞일 때

## 계속 제외하는 대안

- 검토 계약을 공용 Skill로 제공: 구현 세션이 같은 맥락과 권한으로 직접 실행할 수 있어 reviewer 경계를 보장하지 못한다.
- 전체 검토 지침을 플랫폼별 agent 파일에 복사: 검토 기준을 고칠 때 한쪽만 바뀌어 판정 결과가 갈릴 수 있다.
- 한 플랫폼의 agent 파일을 다른 플랫폼에 맞춰 변환: 도구, 권한과 모델 설정 형식이 달라 변환 규칙이 또 하나의 실행 계층이 된다.
