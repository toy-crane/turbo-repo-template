# 모바일 코드 구조

## 결정

- 모바일 제품 코드는 업무 영역을 먼저 나누고, 각 업무 영역 안에서 `Types → Config → Repo → Service → Runtime → UI` 책임 단계를 사용한다.
- 여섯 책임 단계를 `apps/mobile/src` 전체에 적용하는 최상위 기술 폴더로 만들지 않는다.

## 경계

- 이 결정은 업무 영역의 목록과 경계, FSD 계층의 사용 범위, 각 책임 단계의 정확한 뜻과 폴더 이름을 확정하지 않는다.
- 여러 업무 영역이 함께 쓰는 앱 초기화와 외부 연동의 소유권은 별도로 정한다.
- 이름이 같다는 이유만으로 여러 업무 영역의 타입, 설정 또는 저장소 코드를 하나의 공용 폴더에 모으지 않는다.

## 이유

전역 기술 폴더를 사용하면 하나의 제품 흐름을 이해하기 위해 저장소 여러 곳을 오가야 하고, 어느 업무 영역이 코드를 소유하는지도 흐려진다. 업무 영역을 먼저 모으면 함께 바뀌는 코드를 가까이 둘 수 있다. 그 안에서 고정된 책임 단계를 사용하면 의존 방향과 각 파일의 역할을 일관되게 검사할 수 있다.

## 재검토 조건

- 실제 구현에서 대부분의 업무 영역이 같은 코드를 반복해 소유해 경계보다 중복 비용이 더 커질 때
- 선택한 책임 단계가 모바일 런타임의 실제 의존 관계를 표현하지 못해 예외가 반복될 때

## 계속 제외하는 대안

- 모바일 전체를 `types`, `config`, `repo`, `service`, `runtime`, `ui` 최상위 폴더로 나누기: 하나의 업무 흐름이 기술 분류별로 흩어지고 소유권이 흐려진다. 업무 영역보다 기술 계층별 변경이 주된 작업 단위가 되는 경우에만 다시 검토한다.

## 보존할 근거

- OpenAI의 Harness Engineering은 고정된 책임 단계를 각 business domain 안에 두고 의존 방향을 구조 검사로 강제한다.
- Feature-Sliced Design은 업무 영역별 slice 안에서 관련 코드를 가까이 두고, 최상위 계층과 slice 사이의 import 규칙을 구분한다.
