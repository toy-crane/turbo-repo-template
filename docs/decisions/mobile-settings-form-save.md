# 모바일 설정 폼 저장

## 결정

- 여러 값을 하나의 초안으로 모아 한 번에 저장하는 설정 화면은 네이티브 헤더 오른쪽의 확정 동작 하나로 저장한다. 화면 안에 별도 저장 버튼을 두지 않는다.
- 확정 동작은 각 플랫폼이 이미 가진 강조 표현으로 그린다. iOS는 `UIBarButtonItem.Style.prominent`, Android는 Material 3의 채운 아이콘 버튼이다. 두 플랫폼 모두 체크 아이콘을 쓴다.
- 저장할 수 있는 상태와 저장할 수 없는 상태를 배경 채움으로 구분한다. 아이콘 색이나 글자 투명도만 바꾸지 않는다.
- 색이 차는 조건은 "바꾼 값이 있고 모든 값이 쓸 수 있을 때"다. 값이 바뀌었어도 하나라도 쓸 수 없으면 컨트롤은 회색으로 남고 그 이유를 입력 묶음 아래 설명 자리에서 말한다. 색이 찬 컨트롤은 언제나 저장으로 이어진다.
- 저장할 수 없는 동안에도 컨트롤은 자리를 지킨다. 숨기거나 다른 자리로 옮기지 않는다.
- 컨트롤의 화면 읽기 이름은 상태와 관계없이 하나로 고정하고, 저장할 수 없는 상태에서는 disabled를 함께 전달한다.
- 저장이 실패하면 입력한 내용을 그대로 두고 컨트롤을 다시 색이 찬 상태로 되돌린다.
- 뒤로 가기가 초안 전체를 버린다. 저장하지 않고 나가면 아무것도 바뀌지 않는다.

## 경계

- 스위치나 선택처럼 누르는 순간 반영하는 설정 행에는 이 패턴을 쓰지 않는다. 초안이 없으므로 저장할 것도 없고, 저장 버튼을 붙이면 켰는데 반영되지 않은 상태가 생긴다.
- 계정 삭제와 로그아웃 같은 파괴적 동작은 이 패턴이 아니라 [모바일 계정 삭제](mobile-account-deletion.md)의 확인창을 따른다.
- 온보딩처럼 흐름의 한 단계인 화면은 화면 안의 전폭 버튼을 유지한다. 설정 화면이 아니다.
- 이 패턴은 네이티브 헤더가 있는 화면에서만 성립한다. 헤더 없는 시트나 전체 화면 모달에는 확정 동작을 둘 자리가 없으므로 별도로 정한다.
- iOS의 `prominent`는 iOS 26부터 동작한다. 앱은 최소 iOS 버전을 26으로 제한하지 않으므로 그보다 낮은 버전에서는 저장 가능 여부가 기존처럼 아이콘 색으로만 구분된다. 이 결정은 낮은 버전을 위한 별도 모양을 만들지 않는다.
- 컨트롤의 색과 크기는 각 플랫폼 기본값을 쓴다. 앱 팔레트를 밀어 넣지 않는 이유는 [모바일 색상 시맨틱](mobile-color-semantics.md)이 소유한다.
- 저장이 도는 동안의 표시는 [모바일 작업 진행 표시](mobile-action-progress.md)가 소유한다. 이 결정은 저장 전후의 상태만 정한다.
- 값이 하나뿐인 편집 화면에도 쓸 수 있지만, 그런 화면은 즉시 적용이 더 나은 경우가 많으므로 만들 때 어느 쪽인지 먼저 정한다.

## 이유

저장 컨트롤이 지금 눌리는지 보이지 않으면 사용자는 눌러 보고서야 알게 된다. 배경 채움은 아이콘 색이나 투명도보다 멀리서도 구분된다. 두 플랫폼이 이미 확정 동작을 위한 강조 표현을 가지고 있으므로 앱이 새 모양을 만들 이유가 없고, 각 플랫폼의 관례도 그대로 지킨다.

색이 찬 컨트롤이 언제나 저장으로 이어지게 하면, 누를 수 있다고 약속해 놓고 눌렀을 때 이유를 설명하는 일이 사라진다. 못 누르는 이유는 컨트롤이 아니라 문제가 있는 값 아래에서 말하는 편이 어디를 고쳐야 하는지 알려 준다.

## 재검토 조건

- iOS 26 미만에서도 저장 가능 여부를 배경 채움으로 구분해야 하거나, Expo Router가 낮은 버전에 같은 강조 표현을 제공한다.
- `@expo/ui`나 Expo Router가 도구막대 버튼의 강조 표현이나 접근성 이름을 다르게 제공한다.
- 초안을 모아 저장하는 화면이 헤더 없는 시트로 열려야 하는 요구가 생긴다.
- 두 플랫폼의 강조색을 서로 맞춰야 한다는 제품 요구가 생긴다.

## 계속 제외하는 대안

- 아이콘 색이나 글자 투명도만 바꾸기: iOS는 흰 원 안 체크의 색만, Android는 글자 투명도만 달라져 실제 기기에서 구분되지 않았다. 배경 채움을 쓸 수 없는 컨트롤이 생길 때만 다시 검토한다.
- 저장할 수 없을 때 컨트롤 숨기기: 화면에 들어온 직후가 곧 빈 자리가 되고, 무엇이 사라졌는지 알 수 없다. 자리 자체가 다른 뜻을 가질 때만 다시 검토한다.
- Apple 화면의 색과 크기를 Android에 그대로 옮기기: 한 플랫폼의 표현을 다른 쪽에 복사하지 않는다는 [모바일 설정 공개 프로필](mobile-profile-settings.md)의 방식과 어긋난다.
- 값이 바뀌기만 하면 색을 채우기: 쓸 수 없는 값이 남아 있어도 누를 수 있다고 약속하게 된다. 검증을 저장 시점에만 할 수 있는 화면이 생길 때만 다시 검토한다.
- 설정 스위치에도 저장 버튼 붙이기: 켰는데 저장하지 않아 반영되지 않은 상태가 생긴다. 스위치가 서버 실패를 사용자에게 되돌려야 할 때만 다시 검토한다.

## 보존할 근거

- iOS `Stack.Toolbar.Button`은 `variant`로 `plain`, `done`, `prominent`를 받는다. `prominent`는 iOS 26부터이며 `UIBarButtonItem.Style`로 이어진다.
- Android `Stack.Toolbar.Button`은 Compose `IconButton`으로 그려져 배경을 채우지 못한다. 채운 원이 필요하면 `@expo/ui/jetpack-compose`의 `FilledIconButton`을 쓴다.
- `@expo/ui/jetpack-compose`의 `Button`에 문자열 자식을 주면 빈 알약만 그려지고, `Text`를 자식으로 주면 렌더 오류가 난다. 채운 배경 위에 글자를 올리는 방법을 이 버전에서는 찾지 못했다.
- Compose `Host` 안의 `FilledIconButton`은 접근성 트리에 이름 없는 `android.view.View`로만 남는다. `Icon`의 `contentDescription`만으로는 버튼 이름이 생기지 않으므로 `Host`에 `accessibilityLabel`, `accessibilityRole`, `accessibilityState`를 준다.
- `@expo/ui/jetpack-compose`의 `semantics` modifier는 `contentType`만 받는다. 접근성 이름을 Compose 쪽에서 붙일 방법이 없다.
