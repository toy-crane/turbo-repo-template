# 모바일 원격 데이터 상태

## 결정

- 모바일 앱은 Supabase에서 조회하고 변경하는 원격 데이터의 비동기 상태와 캐시를 TanStack Query로 관리한다.
- Supabase 클라이언트는 네트워크 요청과 타입이 지정된 API를 담당한다.
- TanStack Query는 쿼리 키, 로딩과 오류, 오래된 상태, 재시도, 재조회, 데이터 변경 후 무효화를 담당한다.
- 모든 쿼리의 기본 `staleTime`은 1분이다. 그동안은 캐시를 최신 데이터로 보고, 명시적인 무효화가 없으면 같은 쿼리를 다시 불러오지 않는다.

## 경계

- Supabase 인증 세션은 TanStack Query 캐시에 저장하지 않는다.
- 화면의 일시적인 입력, 모달 열림 여부와 같은 로컬 UI 상태를 TanStack Query로 관리하지 않는다.
- 쿼리와 데이터 변경 함수는 Supabase 타입 전용 공유 패키지에 넣지 않는다. 실제 데이터를 사용하는 앱 영역에 둔다.
- 아이디 중복 확인처럼 답이 바로 달라질 수 있는 쿼리는 `staleTime: 0`으로 덮어쓰고 그 이유를 쿼리 가까이에 남긴다.
- 1분은 데이터가 캐시에 남는 시간, 재시도 횟수, 앱 복귀 또는 네트워크 재연결 시점을 정하지 않는다. 이 정책은 각각 별도로 정한다.

## 이유

Supabase 클라이언트만 사용하면 화면마다 로딩, 오류, 중복 요청, 재조회와 데이터 변경 후 동기화를 직접 구현해야 한다. TanStack Query를 원격 상태 계층으로 사용하면 Supabase의 타입이 지정된 쿼리를 유지하면서 이 생명주기를 일관되게 관리할 수 있다.

TanStack Query는 기본적으로 데이터를 받자마자 오래된 것으로 판단한다. 그러면 탭 이동이나 화면 재진입으로 같은 쿼리가 다시 연결될 때 불필요한 요청이 생길 수 있다. 1분 동안 최신 데이터로 보면 짧은 화면 이동은 캐시로 처리하면서도 오래된 데이터를 길게 유지하지 않는다. 데이터 변경 뒤 `invalidateQueries()`나 `setQueryData()`를 사용하는 흐름은 이 시간과 관계없이 즉시 캐시를 갱신할 수 있다.

## 재검토 조건

- 모바일 앱이 원격 데이터를 반복 조회하거나 변경하지 않는 단순한 구조로 축소될 때
- Supabase가 앱의 요구를 충족하는 공식 원격 상태 캐시 계층을 제공할 때
- 주 데이터 경로가 서버 원격 상태가 아니라 완전한 오프라인 우선 동기화 데이터베이스로 바뀔 때
- 실제 요청량이나 사용자 검증에서 1분이 지나치게 짧거나 오래된 데이터를 너무 오래 보여 준다는 결과가 나올 때

## 계속 제외하는 대안

- Supabase 요청 상태를 화면별 `useEffect`와 `useState`로 관리: 중복 요청, 캐시와 무효화 규칙이 화면마다 분산된다. 원격 데이터 화면이 한두 개로 영구히 제한될 때만 재검토한다.
- 기본 `staleTime: 0` 유지: 짧은 화면 이동에도 같은 데이터를 다시 요청할 수 있다. 대부분의 원격 데이터가 항상 최신이어야 한다는 요구가 생기면 다시 검토한다.
- 기본 `staleTime: Infinity` 사용: 명시적인 무효화를 놓치면 앱을 다시 열 때까지 오래된 데이터가 남는다. 모든 원격 데이터의 변경 경로를 앱이 통제하게 되면 다시 검토한다.
