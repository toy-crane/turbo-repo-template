# 모바일 프로필 식별자와 온보딩

## 결정

- 로그인한 계정은 닉네임과 아이디를 모두 정한 뒤에만 앱 화면에 들어간다. 두 값이 모두
  있으면 온보딩을 마친 것으로 판단하며 별도의 `onboarding_completed` 상태는 두지 않는다.
- `profiles.display_name`은 화면에서 "닉네임"이라고 부른다. 프로필에 표시되는 사용자가
  바꿀 수 있는 값이며 1–30자로 제한한다.
- `profiles.username`은 화면에서 "아이디"라고 부른다. 다른 계정과 대소문자 구분 없이
  겹치지 않는 공개 계정 식별자다. 저장할 때 영문 소문자로 정규화하고 영문 소문자,
  숫자와 밑줄만 허용하며 길이는 3–20자로 제한한다.
- 아이디 값과 화면 표기에는 `@`를 붙이지 않는다.
- 로그인한 사용자는 앱 안에서 다른 사용자의 공개 프로필을 볼 수 있다. 공개 프로필은
  프로필 사진, 닉네임과 아이디로 구성한다.
- 프로필 사진 파일은 공개 자산으로 제공한다. 파일을 읽을 때는 로그인을 요구하지 않지만,
  업로드, 교체와 삭제는 프로필 소유자만 할 수 있다.
- 온보딩은 닉네임과 아이디를 차례로 받는 두 화면으로 구성한다. 큰 본문 제목은 각각 `닉네임을 정해 주세요`와 `아이디를 정해 주세요`를 사용한다. 두 화면은 높이가 같은 네이티브 헤더 틀을 사용하고, 들어가면 입력창에 자동으로 포커스한다.
- 닉네임 화면에는 뒤로가기를 두지 않는다. 아이디 화면에서 닉네임 화면으로 돌아가면 두 입력값을 유지한다. 앱을 다시 열면 임시 입력을 복원하지 않고 닉네임 화면부터 시작한다.
- 제공자 이름은 닉네임의 편집 가능한 초기값으로 사용한다. 이메일의 `@` 앞부분에서 `+` 뒤를 버리고, 영문을 소문자로 바꾸고, 영문·숫자·밑줄 이외의 문자를 제거한 뒤 20자로 잘라 아이디 후보를 만든다. 결과가 3자보다 짧으면 비워 둔다.
- 형식이 맞는 아이디는 입력을 멈추면 자동으로 사용 가능 여부를 확인한다. 이미 사용 중이거나 예약된 값이면 서버가 사용 가능하다고 확인한 대안 세 개를 보여 준다. 최종 저장은 데이터베이스 제약으로 다시 판정한다.
- 닉네임과 아이디는 한 번의 프로필 변경으로 함께 저장한다. 확인이나 저장이 실패하면 두 입력값을 유지하고 같은 화면에서 다시 시도할 수 있게 한다.
- `프로필` 화면은 프로필 사진, 닉네임과 아이디를 한 번에 수정한다. 프로필 사진을 삭제하면 닉네임의 첫 글자를 대신 보여 주며, 로그인 제공자의 사진을 나중에 다시 자동으로 채우지 않는다.
- 기본 예약 아이디는 `admin`, `administrator`, `support`, `official`, `system`이다. 파생 프로젝트는 운영 사용자를 받기 전에 프로젝트 슬러그와 실제 서비스 운영 명칭에서 필요한 예약어를 추가한다.
- 아이디는 영구 불변 식별자로 취급하지 않는다. `프로필` 화면에서 아이디 변경이 성공한 시점부터 30일 동안 다시 바꿀 수 없다.
- 아이디를 바꾸면 이전 아이디도 같은 시점부터 30일 동안 다른 계정에 배정하지 않는다. 변경 제한과 이전 아이디 보호가 끝나는 시각은 서버가 판정한다.

## 경계

- 공개 프로필은 로그인한 사용자가 앱 안에서 보는 화면이다. 로그인 없이 여는 웹 프로필,
  아이디 기반 주소, 검색과 멘션은 아직 제공하지 않는다. 이런 기능을 추가할 때 같은
  아이디를 재사용할지와 변경 이력을 어떻게 처리할지 다시 정한다.
- `auth.users.id`가 내부 관계와 권한의 기준이다. 아이디를 외래 키나 변경 불가능한 내부
  식별자로 사용하지 않는다.
- 제공자 이름과 이메일에서 만든 값은 편집 가능한 후보일 뿐이다. 사용자가 마지막 동작을
  실행하기 전에는 아이디로 확정하지 않는다.
- 프로필 조회 실패는 로그아웃으로 취급하지 않는다. 앱 화면을 열지 않고 같은 자리에서 다시 조회할 수 있게 한다.
- 온보딩 화면에는 규칙 설명, 단계 표시와 건너뛰기를 두지 않는다. 필요한 형식 오류와 요청 실패만 입력란 가까이에서 알려 준다.
- 아이디 변경 제한 중에도 프로필 사진과 닉네임은 바꿀 수 있다. 화면은 아이디 입력만 비활성화하고 다시 바꿀 수 있는 날짜를 보여 준다.
- 성공한 아이디 변경을 즉시 취소하거나 이전 아이디로 되돌리는 별도 경로는 제공하지 않는다.
- 현재 운영 사용자가 없다는 전제에서 도입한다. 기존 사용자 안내와 프로필 값 백필은
  포함하지 않는다.

## 이유

닉네임과 아이디가 실제로 있어야 하는데 별도의 완료 상태까지 저장하면 값과 상태가 서로
어긋날 수 있다. 두 필드 자체를 완료 조건으로 쓰면 프로필의 실제 상태만 확인하면 된다.
아이디는 사람이 보고 입력하는 공개 이름이므로 내부 관계의 기준과 분리해야 나중에 값을
바꾸더라도 다른 데이터가 끊기지 않는다.

공개 프로필은 다른 사용자가 계정을 알아보는 데 필요한 값만 보여 준다. 인증과 관계의
기준은 계속 `auth.users.id`로 유지하므로 공개 프로필 값이 바뀌어도 계정 소유권과 기존
데이터 관계는 바뀌지 않는다.

`@`는 멘션이나 주소 문법이 있을 때 의미가 있지만 현재 화면에는 그 문법이 없다. 지금
붙이면 아직 제공하지 않는 기능을 암시하고 입력값과 표시값도 다르게 만든다.

후보를 편집할 수 있게 하고 마지막 저장에서 데이터베이스 제약을 다시 확인하면 입력 편의와 동시 요청의 정확성을 함께 지킬 수 있다. 두 값을 함께 저장하면 온보딩 완료 조건과 프로필 값이 일부만 바뀌는 상태를 만들지 않는다.

30일 제한은 아이디를 자주 바꿔 다른 계정처럼 보이는 일을 줄인다. 이전 아이디도 같은 기간 보호하면 다른 사람이 바로 가져가서 이전 계정으로 오해받는 일을 막을 수 있다. 프로필 사진과 닉네임은 계속 바꿀 수 있게 두어 아이디 제한이 다른 프로필 관리를 막지 않게 한다.

## 재검토 조건

- 검색, 멘션 또는 공개 프로필 주소를 만들 때
- 아이디 변경 주기, 이전 아이디 보호 기간 또는 이전 아이디를 넘겨주는 정책을 바꿀 때
- 운영 사용자가 생긴 뒤 필드 제약이나 필수 온보딩을 다시 바꿀 때

## 계속 제외하는 대안

- 별도 온보딩 완료 열: 필수 필드가 비어 있는데 완료로 표시되는 모순 상태를 추가한다.
- 화면에 항상 `@` 표시: 현재 제품에는 `@`가 나타내는 멘션이나 주소 기능이 없다.
- 아이디를 영구 고정: 이메일 기반 후보를 확정한 사용자가 나중에 바로잡을 방법이 없어진다.
- 아이디를 제한 없이 바로 다시 변경: 다른 계정처럼 보이거나 이전 아이디를 가져간 계정과 혼동할 가능성이 커진다.
