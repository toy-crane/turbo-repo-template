# 05: 메시지 작업과 새 대화

## 결과

각 메시지 아래에 작업 영역이 생긴다. 모든 사용자·AI 메시지는 본문을 복사할 수 있고, 마지막 사용자 메시지만 `편집 후 다시 보내기`, 마지막 AI 답변만 `다시 생성`을 제공한다. 편집은 하단 입력창을 재사용한다. 원문이 입력창에 채워지고 편집 중 표시와 취소가 보이며, 전송하면 메시지가 교체되고 이전 답변이 사라진 뒤 새 답변을 받는다. Home 헤더에는 새 대화 버튼이 생겨 메시지가 있으면 복구 불가 확인 뒤 현재 대화만 지운다. 생성 중에는 이 작업들이 모두 잠긴다.

## 선행 조건

- 02: 작업 버튼이 붙는 메시지 행, 편집 배너가 붙는 입력창, 새 대화 버튼이 쓰는 세션 소유 구조가 02에서 만들어진다.

## 완료 조건

- [x] UI 배선 전에 확정 테스트를 먼저 작성한다: 편집 전송 후 가짜 transport의 `sendMessages`가 받은 메시지 목록이 편집된 사용자 메시지로 끝나고 이전 AI 답변을 포함하지 않는다(hook 테스트). 실패하면 `setMessages` 잘라내기 + `regenerate()` 대안으로 구현을 바꾼다.
- [x] 모든 사용자·AI 메시지 아래 작업 영역이 있고 본문을 복사할 수 있다. 복사는 텍스트 part를 빈 줄로 이어 클립보드에 넣고, 화면 표시는 계속 part 단위를 유지한다. 복사 후 `복사됨` 피드백이 색이 아닌 신호로 잠시 보인다.
- [x] 마지막 사용자 메시지에만 `편집 후 다시 보내기`가 보인다. 누르면 입력창에 원문이 채워지고 편집 중 표시와 `편집 취소`가 보이며, 취소하면 편집 전 초안이 복원된다.
- [x] 편집 상태에서 전송하면 마지막 사용자 메시지가 새 내용으로 교체되고 그 뒤의 AI 답변이 사라진 뒤 새 답변을 받는다. 요청은 기존 `POST /ai/chat` 하나로 간다.
- [x] 마지막 AI 답변에만 `다시 생성`이 보이고, 누르면 정확히 한 번 재요청한다. `다시 생성`은 `ready` 상태에서만 활성이다(오류 상태의 재시도는 기존 `다시 보내기`가 담당).
- [x] Home 헤더 도구 막대에 새 대화 버튼이 있다(iOS는 SF Symbol, Android는 텍스트 레이블). 메시지가 있으면 복구할 수 없다는 플랫폼 기본 Alert 확인 뒤 메모리 상태만 비우고, 비어 있으면 확인 없이 그대로다. 서버에 초기화 요청을 보내지 않는다.
- [x] `submitted`·`streaming` 동안 전송, 편집, 다시 생성, 새 대화가 모두 비활성이거나 무동작이고, 기존 `running` ref 가드가 편집 전송까지 덮는다.
- [x] `메시지 복사`, `편집 후 다시 보내기`, `편집 취소`, `다시 생성`, `새 대화` 이름이 `chatLabels`와 README 접근성 표에 같은 커밋으로 추가된다.
- [x] 모든 작업 버튼이 44pt 터치 영역과 접근성 이름·역할을 갖고, VoiceOver와 TalkBack으로 식별·실행된다.

## 제약

- 과거 사용자 메시지 편집과 과거 AI 답변 다시 생성은 만들지 않는다.
- 새 대화 버튼 배치는 02의 `Stack.Toolbar` 프로브 결과를 따른다. `HomeScreen` 내부 등록이 안 되면 라우트 파일(`app/(tabs)/(home)/index.tsx`)이 조립을 맡는다.
- 클립보드는 02에서 설치한 `expo-clipboard`를 사용한다. 새 의존성을 추가하지 않는다.

## 실행 결과

- 검증: `bun run check`, `bun run check-types`, `bun run test`(141개) 모두 통과.
- 확정 테스트를 UI 배선 전에 작성했고 통과했다: 편집 전송 후 가짜 transport가 받은 목록은 편집된 사용자 메시지 하나로 끝나고 이전 AI 답변을 포함하지 않는다. `setMessages` 잘라내기 + `sendMessage` 방식이 첫 시도에 검증되어 대안(`regenerate()`)은 쓰지 않았다.
- 기기 검증(iOS): 메시지 복사(클립보드 원문 일치, 복사됨 피드백), 편집 취소 경로(배너·원문 채움·초안 복원), 편집 확정 경로(마지막 사용자 메시지 교체, 이전 답변 소멸, 새 답변 하나, 이전 히스토리 유지), 다시 생성(생성 중 상태로 실제 재요청), 새 대화(빈 대화 무확인 유지, 메시지 있으면 Alert 후 초기화), 생성 중 잠금(비활성 스타일), 헤더의 SF Symbol 새 대화 버튼과 아바타.
- 기기 검증(Android): 작업 버튼 3종 표시와 TalkBack 이름, 복사와 복사됨, 편집 시작(배너·원문), 새 대화 텍스트 레이블 버튼, 빈 대화 무확인, Alert 확인 뒤 초기화. Android 헤더 탭이 dev 메뉴를 열던 함정은 `headerRight` 경로에서는 재현되지 않았다.
- 배치 변경 기록: `Stack.Toolbar`는 쓰지 못했다. Android의 `Stack.Toolbar.Button`은 이미지 아이콘 없이는 null을 그리고(텍스트 레이블 미지원), 커스텀 `Stack.Toolbar.View`는 Jetpack Compose 제약 측정 크래시(`Can't represent a width of 520192...`)를 일으켰다. 대신 `navigation.setOptions({ headerRight })`로 새 대화 버튼과 아바타를 한 곳에서 그린다(iOS는 SF Symbol, Android는 텍스트 레이블 — 작업 원안 유지). 이에 따라 아바타 등록도 라우트 파일에서 `HomeScreen`으로 옮겼고 라우터 테스트의 아바타 press 검증은 home-screen 테스트로 이동했다.
- jest 한계 기록: 가상 목록 컨테이너는 jest에서 네이티브 레이아웃을 받지 못해 `pointerEvents: "none"` 뒤에 남고 행 내부 press가 조용히 무시된다. 02의 대응 사다리 마지막 단계대로 chat-panel 테스트는 데이터를 그대로 매핑하는 목록 목을 쓴다(실제 목록 동작은 기기 검증이 담당).
- 선행 조건: 02의 행·입력창·세션 소유 구조를 그대로 사용했다.
