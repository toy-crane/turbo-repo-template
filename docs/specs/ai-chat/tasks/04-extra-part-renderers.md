# 04: 파일·출처·도구 part 표시

## 결과

AI 답변에 파일, 출처, 도구 part가 섞여 들어와도 UI가 종류와 순서대로 표시한다. 파일 part는 파일 이름, 종류와 열기 작업을, 출처 part는 제목과 출처 주소를, 도구 part는 실행 중·완료·실패 상태와 결과를 보여준다. 도구별 전용 UI를 등록할 수 있고, 전용 UI가 없거나 알 수 없는 part도 앱을 중단시키지 않는 안전한 기본 표시로 그려진다. 실제 서버는 계속 텍스트만 보내며 이 표시들은 가짜 데이터로 검증한다.

## 선행 조건

- 02: part 렌더러 분기 구조와 가짜 transport 테스트 기반이 이 작업의 토대다.

## 완료 조건

- [ ] 파일 part가 파일 이름, 종류와 열기 작업을 보여준다.
- [ ] 출처 part(`source-url`, `source-document`)가 제목과 출처를 식별할 수 있게 보여주고 원문을 열 수 있다.
- [ ] 도구 part가 실행 중, 완료, 실패 상태를 구분해 표시하고 결과를 보여준다.
- [ ] 도구별 전용 UI 등록점(레지스트리)이 있고, 테스트가 가짜 렌더러를 등록해 기본 표시를 대체하는 것을 증명한다. MVP 기본 상태의 레지스트리는 비어 있다.
- [ ] 승인 대기·응답 상태와 미지원 part(`data-*`, `custom`, 미래 종류)는 승인·거절 버튼 없이 안전한 기본 표시로 그려지고, 이웃 part의 순서가 유지된다.
- [ ] `step-start` part는 아무것도 그리지 않는다.
- [ ] 텍스트, 파일, 출처, 도구가 섞인 가짜 스트림에서 part 종류와 순서가 들어온 대로 유지된다.

## 제약

- 실제 서버 응답에 파일, 출처, 도구 part를 추가하지 않는다. 검증은 컴포넌트 테스트의 가짜 데이터로 한정한다(스펙이 정한 범위).
- 도구 승인·거절 UI를 만들지 않는다.
- 렌더러 분기는 설치된 AI SDK의 타입 가드(`isTextUIPart`, `isFileUIPart`, `isToolUIPart` 등)를 사용한다.

## 검증

- 저장소 루트에서 다음 명령이 모두 통과한다.
  - `bun run check --filter=@repo/mobile`
  - `bun run check-types --filter=@repo/mobile`
  - `bun run test --filter=@repo/mobile`
- 이 작업의 확정 근거는 컴포넌트 테스트다. 기기 검증은 필요하지 않다.
