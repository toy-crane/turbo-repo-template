# 개발 세션 상태 보기와 한 줄 시작

## 사용자에게 보이는 결과

- 상태 조회 명령 하나로 모든 worktree의 slot, 포트, 프로세스 생존 여부, 붙어 있는 플랫폼, 배정된 기기를 한 번에 본다. 어느 기기와 어느 Metro가 어느 worktree의 것인지 찾으려고 `xcrun simctl list`와 adb를 뒤지지 않는다.
- 배정된 기기의 이름만 보고 어느 worktree의 기기인지 알아본다. 이름이 비슷한 다른 worktree의 기기를 조작하는 실수가 사라진다.
- `bun run dev ios android` 한 줄로 두 플랫폼을 함께 시작한다.
- `bun run dev`를 인수 없이 실행하면 지금처럼 아무것도 시작하지 않고, 사용법 안내에서 여러 플랫폼을 나열하는 형태를 배운다.

## 승인한 범위

- 읽기 전용 상태 조회 명령을 추가한다.
- 배정된 기기 이름에 배정 정보를 표시한다.
- 시작 명령이 플랫폼 인수를 여러 개 받도록 확장한다. 적은 순서가 시작 순서다.
- 이 변경이 요구하는 조항을 결정 계약 [Worktree 개발 세션](../../decisions/worktree-development-sessions.md)에서 갱신한다. 이전 명세 [한 worktree에서 두 플랫폼 함께 검증](../worktree-dual-platform-session/spec.md)이 미뤄 둔 "한 줄 동시 시작"과 "상태 조회 명령"을 이 명세가 이어받는다.

## 관찰 가능한 인수 기준

상태 조회:

1. 상태 명령은 각 worktree의 경로와 라벨, slot, API 포트, Metro 포트, API·Metro 프로세스의 생존 여부, 붙어 있는 플랫폼, 플랫폼별 기기 이름과 UDID(Android는 AVD 이름과, 실행 중이면 adb serial)를 보여 준다.
2. 상태 명령은 아무것도 바꾸지 않는다. 프로세스를 시작하거나 중지하지 않고, slot·기기 배정·상태 파일을 고치지 않는다. 세션이 하나도 없어도 성공하고 "없음"을 보여 준다.
3. 풀에 있지만 배정되지 않은 기기도 함께 보여 준다.

기기 배정 표시:

4. 배정된 iOS Simulator는 기기 목록(Simulator 앱, `xcrun simctl list`)의 이름만 보고 어느 worktree의 기기인지 알 수 있다.
5. 기기 이름 표시는 UDID, 설치된 앱, 앱 데이터와 로그인 상태를 보존하고, native fingerprint와 공용 빌드 재사용에 영향을 주지 않는다.

한 줄 시작:

6. 아무것도 실행 중이지 않은 worktree에서 `bun run dev ios android`가 끝나면, 두 기기의 앱이 모두 이 worktree의 Metro에 붙어 있다.
7. 세션이 이미 실행 중인 worktree에서도 여러 플랫폼을 적은 명령이 끝나면, 적은 플랫폼의 앱이 모두 이 worktree의 Metro에 붙어 있다. 재사용과 재시작 판단은 플랫폼을 하나씩 차례로 시작할 때와 같은 기존 규칙을 따른다.
8. 아무것도 실행 중이지 않은 실행에서 필요한 네이티브 빌드는 Metro가 뜨기 전에 끝난다. 빌드가 도는 동안 이 worktree의 Metro 프로세스는 살아 있지 않다.
9. 한 플랫폼이 실패해도 나머지 플랫폼의 시작을 시도한다. 결과를 플랫폼별로 보고하고, 실패가 하나라도 있으면 명령은 실패로 끝난다.
10. `--clear`는 여러 플랫폼을 적어도 Metro 캐시를 한 번만 초기화한다.
11. 플랫폼 하나만 적는 기존 명령과 누적 실행은 지금과 똑같이 동작한다.
12. `bun run dev`는 아무것도 시작하지 않고, 사용법에 `bun run dev ios android` 형태를 안내한다.

## 정해진 제약과 이유

- **인수 없는 `bun run dev`는 계속 아무것도 시작하지 않는다.** 주요 모바일 CLI 중 빈 명령으로 기기를 켜는 도구는 없다. Expo `expo start`는 서버만 띄우고 키 입력을 기다리고, Flutter는 기기 선택지를 보여 주며, Capacitor는 플랫폼이 필수 인수다. 기기 부팅과 네이티브 빌드가 비싸기 때문에 이 계열은 명시를 강제한다. 빈 명령이 두 플랫폼을 켜면 가장 치기 쉬운 명령이 가장 비싼 실행이 되고, Android 도구가 없는 컴퓨터에서는 항상 절반만 성공하는 명령이 된다.
- **여러 대상은 가변 위치 인수로 나열한다.** `docker compose up [SERVICE...]`, GNU Make의 다중 goal, `gradle clean build`가 같은 형태다. 새 단어 없이 "플랫폼 명시 필수" 규칙을 유지하고 `--clear` 같은 옵션과 그대로 조합된다. `all` 키워드는 모바일 쪽 선례가 Flutter의 문서화되지 않은 `-d all` 하나뿐이라 채택하지 않는다.
- **상태 명령은 읽기 전용이다.** 사라진 worktree의 자원 회수는 결정 계약대로 시작 명령의 몫이다. 조회가 상태를 바꾸면 언제든 안전하게 실행할 수 없다.
- **기기 표시는 앱 정체성을 건드리지 않는다.** 앱 이름, slug, 번들 ID를 worktree마다 바꾸면 native fingerprint가 갈려 공용 빌드 공유가 깨진다. 표시는 기기 이름과 상태 출력에서만 한다.
- **호스트·포트 판단이 사는 환경 모듈은 `apps/mobile` 안에 남긴다.** 개발 모드의 `EXPO_PUBLIC_*` 치환은 `node_modules` 실경로의 파일에는 적용되지 않으므로, 이 모듈을 공유 패키지로 옮기면 조용히 깨진다.

## 가정

뒤집어도 되는 판단이며, 어긋나면 이 명세를 고친다.

- 상태 명령 이름은 `bun run dev:status`다. `dev:stop`, `dev:remove`와 나란한 이름이고, `bun run dev status`는 플랫폼 인수 자리와 겹쳐 쓰지 않는다.
- iOS 기기 이름은 배정할 때 worktree를 알아볼 수 있게 바꾸고 반납할 때 풀 이름으로 되돌린다.
- Android는 AVD `config.ini`의 표시 이름에 같은 표시를 쓴다. 에뮬레이터가 새로 뜨기 직전에만 쓰고, 확인 결과 Android Studio와 `dev:status`에서 읽힌다.
- 두 플랫폼의 네이티브 빌드가 모두 필요하면 차례로 빌드한다. 병렬 빌드는 하지 않는다.

## 손대지 않는 곳

- **slot·포트·기기 배정 구조, 공용 네이티브 빌드, Metro 캐시 격리, Supabase 공유.** 이번 외부 조사(Expo 1차 자료, 커뮤니티 도구, CLI 관례)가 유지를 확인한 핵심 구조다.
- **dev launcher(mDNS) 목록에 표시되는 서버 이름.** 앱 정체성에 묶여 있어 바꾸면 공용 빌드가 깨진다. worktree 구분은 포트와 상태 명령의 매핑으로 한다.
- **`dev:stop`과 `dev:remove`의 동작 범위.**

## 미룬 것

- `dev all` 같은 전체 별칭. 필요가 확인되면 가변 위치 인수 위에 얹는다.
- 상태 명령의 기계 판독 출력(JSON).
- 실행 중인 세션에 플랫폼을 더할 때(join) 네이티브 빌드가 살아 있는 Metro 아래에서 도는 문제. [열린 follow-up](../../follow-ups/dev-session-native-build-runs-under-live-metro.md)의 검증 결과를 기다린다. 이 명세의 8번 기준은 아무것도 실행 중이지 않은 한 줄 시작에만 적용된다.
- 두 플랫폼 네이티브 빌드의 병렬 실행.

## 남은 위험

- 기기 이름 표시는 최선 노력이다. 이름 변경이 실패해도 부팅과 세션 시작은 이어지고, 다른 worktree가 빌린 기기가 원하는 이름을 쓰고 있으면 이번 변경을 미룬다. 그래서 4번 기준이 잠시 어긋날 수 있으며, 그때는 `dev:status`가 보여 주는 UDID와 slot 매핑이 기준이다.
- 같은 slug를 쓰는 저장소 clone이 둘이면 상태 파일이 따로라서 두 clone의 같은 slot 기기가 같은 이름을 두고 다툴 수 있다. 한 컴퓨터에 한 clone을 두는 지금 쓰임에서는 생기지 않는다.
- Android 표시 이름은 에뮬레이터가 새로 뜨기 직전에만 `config.ini`에 쓴다. 반납할 때 지우는 쓰기는 에뮬레이터가 종료 직후 파일을 다시 쓰는 순간과 겹칠 수 있어, 풀로 돌아간 AVD에 이전 표시가 잠시 남을 수 있다. 다음 배정의 새 부팅이 덮어쓴다.
- iOS 기기 이름이 배정마다 바뀌면, 이전 이름을 기억한 도구나 기록은 다음 배정에서 그 이름을 찾지 못한다. 이름이 정확해지는 대가이며 상태 명령이 현재 이름을 보여 준다.
- 두 플랫폼의 첫 실행을 한 줄로 몰면 빌드 두 개를 차례로 기다린다. 총 대기 시간은 각각 실행할 때의 합과 같지만 한 번에 몰려서 길게 느껴질 수 있다.
