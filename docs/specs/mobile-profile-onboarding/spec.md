# 모바일 프로필 온보딩 명세

## 목표

로그인을 마친 새 계정이 앱에 들어가기 전에 닉네임과 고유한 아이디를 정하게 한다. 두
화면만 사용하고, 제공자 이름과 이메일에서 편집 가능한 후보를 만들어 처음부터 입력해야
하는 부담을 줄인다. 아이디 형식과 중복은 필요한 순간에만 알려 주며 화면을 규칙 설명으로
채우지 않는다.

[모바일 인증](../../decisions/mobile-authentication.md)의 로그인 방식, 세션 생명주기와 로컬
인증 검증 경로는 그대로 둔다. 이 명세는 로그인 뒤 필수 온보딩과 `profiles.username`만
추가한다.

## 필요한 최종 상태

### 진입과 완료 조건

- Supabase 세션이 생기면 자기 프로필을 읽은 뒤 보호 경로를 고른다.
- `display_name`과 `username`이 모두 있으면 기존 `(tabs)` 앱 화면을 연다.
- 둘 중 하나라도 없으면 앱 화면 대신 필수 프로필 온보딩을 연다. 별도의
  `onboarding_completed` 열은 만들지 않는다.
- 세션과 프로필 확인이 끝나기 전에는 로그인, 온보딩 또는 앱 화면을 먼저 보여 주지 않는다.
- 프로필을 읽지 못하면 앱 화면을 열지 않고 같은 화면에서 다시 시도할 수 있는 오류를
  보여 준다. 읽기 실패를 로그아웃으로 취급하지 않는다.
- 온보딩을 마치면 별도 반환 목적지 없이 현재 로그인 흐름의 기본 목적지인 홈 탭을 연다.
- 온보딩 중에는 앱 화면으로 건너뛰는 경로를 제공하지 않는다.

현재 운영 사용자가 없으므로 기존 사용자용 안내, 값 백필과 단계별 마이그레이션은 만들지
않는다. 스키마에 추가하는 `username`은 온보딩 전 상태를 표현할 수 있게 `null`을 허용한다.

### 화면 흐름

온보딩은 같은 Native Stack 안의 두 화면이다.

| 화면 | 제목 | 보이는 레이블 | 주 동작 |
| --- | --- | --- | --- |
| 닉네임 | `닉네임을 정해 주세요` | `닉네임` | `다음` |
| 아이디 | `사용할 아이디를 입력해 주세요` | `아이디` | `시작하기` |

- 닉네임 화면의 `다음`은 [화면 문구 한국어 말투](../../decisions/korean-ui-writing.md)가
  일반적으로 피하는 문구의 기능 한정 예외다. 이 동작은 값을 저장하거나 아이디를 만드는
  동작이 아니라 다음 입력 화면으로만 이동하므로, 목적지를 쓴 `아이디 정하기`보다 `다음`이
  현재 행동을 정확하게 전달한다.
- 두 화면 모두 제목, 입력란과 주 동작만 둔다. 설명 문구, 규칙 목록, `1/2` 표시와 진행
  막대를 두지 않는다.
- 닉네임 화면은 온보딩의 첫 화면이므로 뒤로가기와 건너뛰기를 두지 않는다.
- 아이디 화면은 네이티브 Stack의 레이블 없는 뒤로가기를 제공한다. 돌아가도 두 입력값과
  현재 아이디 후보를 유지한다.
- 아이디 화면을 새로고침하거나 앱 내비게이션 상태가 복원되지 않으면 닉네임 화면부터
  다시 시작한다. 임시 온보딩 상태를 서버에 따로 저장하지 않는다.
- 화면을 열면 입력란에 커서를 두고 키보드를 올린다. 주 동작은 기존 인증 화면과 같이
  키보드 바로 위에 남는다.
- 아이디 입력과 표시에는 `@`를 붙이지 않는다.

### 닉네임

- Google과 Apple이 제공한 이름 또는 프로필에 이미 있는 `display_name`을 편집 가능한
  초기값으로 보여 준다. 이메일 로그인에는 닉네임 초기값이 없다.
- 제공자 로그인이 세션을 만든 직후 빈 프로필 값을 채우는 현재 흐름을 유지한다. 프로필을
  먼저 읽었더라도 제공자 값 저장이 끝나면 해당 원격 상태를 갱신해 온보딩 첫 화면에
  닉네임 후보가 나타나게 한다.
- 사용자가 `다음`을 누르기 전까지 초기값을 그대로 쓰거나 바꿀 수 있다.
- 닉네임은 한글, 영문, 숫자, 공백과 이모지를 허용하며 1~30자로 제한한다.
- 앞뒤 공백은 저장할 값에서 제거하고 중간 공백은 보존한다. 공백만 있는 값은 빈 값으로
  취급한다.
- 빈 값이나 30자를 넘는 값으로는 다음 화면에 갈 수 없다. 오류는 입력란 바로 아래에
  해결 방법을 보여 준다.
- `다음`은 서버에 값을 저장하지 않고 아이디 화면으로 이동한다.

### 이메일 기반 아이디 후보

아이디 화면을 처음 열면 로그인한 이메일에서 다음 순서로 초기 후보를 만든다.

1. `@` 앞부분만 남긴다.
2. `+`부터 뒤에 붙은 메일 분류용 문자열을 제거한다.
3. 영문을 소문자로 바꾼다.
4. 영문, 숫자와 밑줄 이외의 문자를 제거한다.
5. 20자를 넘으면 뒤를 잘라낸다.
6. 결과가 3자보다 짧으면 입력란을 비워 둔다.

예시는 다음과 같다.

| 이메일 | 초기 후보 |
| --- | --- |
| `toy.crane+news@example.com` | `toycrane` |
| `MY_ID@example.com` | `my_id` |
| `hello-world@example.com` | `helloworld` |

- 후보는 입력란에 미리 채우되 사용자가 전부 바꿀 수 있다. Apple 비공개 릴레이처럼
  의미 없는 주소에서도 자동 확정하지 않는다.
- 첫 후보가 이미 사용 중이거나 예약된 값이면 원래 후보에 임의의 숫자를 붙여 사용할 수
  있는 대안 세 개를 보여 준다. 후보는 20자를 넘지 않으며 서버에서 사용 가능함을 확인한
  값만 포함한다.
- 대안은 생년, 가입 연도나 다른 개인정보를 조합하지 않는다. 예시는 `toycrane17`,
  `toycrane24`, `toycrane_7`이다.
- 대안을 누르면 입력란에 반영하고 직접 입력한 값과 같은 검증을 다시 거친다. 첫 후보를
  사용할 수 있으면 대안 목록은 보여 주지 않는다.

### 아이디 입력과 중복 확인

- 아이디는 3~20자의 영문 소문자, 숫자와 밑줄만 허용한다. 밑줄은 처음, 끝 또는 연속된
  위치에도 쓸 수 있다.
- 직접 입력하거나 붙여 넣은 영문 대문자는 즉시 소문자로 바꾼다. 그 밖의 허용되지 않는
  문자는 조용히 지우지 않고 입력란 가까이에 오류로 알려 준다.
- 형식이 맞는 입력을 잠시 멈추면 별도 `중복 확인` 버튼 없이 자동으로 사용 가능 여부를
  확인한다.
- 확인 중에는 로딩 상태를, 사용할 수 있으면 체크 표시를 보여 준다. 정상 상태에는 규칙
  문장이나 성공 문구를 계속 표시하지 않는다.
- 형식이 잘못됐거나 확인 중이거나 이미 사용 중이면 `시작하기`를 누를 수 없다. 사용
  가능함을 확인한 뒤에만 버튼을 활성화한다.
- 자동 확인은 입력 편의를 위한 결과다. `시작하기`를 누르면 데이터베이스의 고유성 제약으로
  다시 판정해 동시에 같은 값을 고르는 경우도 막는다.
- 자동 확인 요청이 실패하면 입력값을 보존하고 다시 확인할 수 있게 한다. 마지막 저장이
  실패해도 두 입력값을 보존하고 같은 화면에서 다시 시도할 수 있게 한다.

오류 문구는 다음을 기준으로 한다.

| 상태 | 문구 |
| --- | --- |
| 허용하지 않는 문자 | `영문 소문자, 숫자, 밑줄(_)만 사용할 수 있어요.` |
| 3자 미만 | `3자 이상 입력해 주세요.` |
| 20자 초과 | `20자 이하로 입력해 주세요.` |
| 중복 | `이미 사용 중인 아이디예요.` |
| 예약 아이디 | `사용할 수 없는 아이디예요.` |
| 확인 요청 실패 | `아이디를 확인하지 못했어요. 다시 시도해 주세요.` |

### 저장과 프로필 상태

- `시작하기`는 닉네임과 아이디를 한 번의 프로필 변경으로 함께 저장한다. 아이디 중복이나
  네트워크 오류가 나면 둘 중 하나만 사용자 입력값으로 반영하지 않는다.
- 최종 저장이 성공하면 프로필 원격 상태를 새 값으로 갱신하고 보호 경로를 홈 탭으로
  전환한다.
- 최종 저장 중에는 같은 동작을 중복 실행하지 못하게 한다. 버튼 문구는 유지하고 진행
  상태만 함께 보여 준다.
- 최종 저장 직전 아이디를 다른 계정이 먼저 사용했다면 중복 오류와 사용할 수 있는 후보
  세 개를 아이디 화면에 보여 준다. 닉네임과 직접 입력한 아이디는 잃지 않는다.

`public.profiles`는 다음 프로필 값 계약을 갖는다.

| 열 | 형식과 규칙 | 용도 |
| --- | --- | --- |
| `display_name` | `text null`, 값이 있으면 앞뒤 공백을 뺀 1~30자 | 화면의 닉네임 |
| `username` | `text null unique`, 값이 있으면 `^[a-z0-9_]{3,20}$` | 공개 계정 아이디 |
| `avatar_url` | 기존 계약 유지 | 프로필 이미지 주소 |

- `username`은 저장 전에 소문자로 정규화하고 데이터베이스에서도 형식, 고유성과 예약어를
  강제한다. 앱 검증이나 중복 확인 호출을 거치지 않은 직접 변경도 같은 규칙을 벗어날 수
  없다.
- 대소문자가 다른 값은 같은 아이디로 취급한다. 저장값이 소문자뿐이므로 데이터베이스의
  고유성도 같은 결과를 낸다.
- 템플릿의 기본 예약어는 `admin`, `administrator`, `support`, `official`, `system`이다.
  파생 프로젝트는 운영 사용자를 받기 전에 영문 프로젝트 슬러그에서 구분 기호를 제거한
  값과 실제 서비스 운영 명칭을 예약어에 추가한다.
- 다른 프로필 행을 읽을 권한은 넓히지 않는다. 사용 가능 확인과 후보 생성은 요청한
  아이디의 상태와 사용 가능한 후보만 돌려주며 다른 사용자의 프로필 값을 노출하지 않는다.
- `auth.users.id`가 관계와 권한의 기준이다. `username`을 다른 테이블의 변경 불가능한 키로
  사용하지 않는다.

### 접근성

- 닉네임과 아이디 입력, 뒤로가기, 후보 선택, `다음`, `시작하기`와 오류 재시도에는 안정된
  접근성 역할과 이름을 둔다.
- 아이디 사용 가능 체크는 색과 아이콘만으로 전달하지 않고 스크린 리더에
  `사용할 수 있는 아이디` 상태로 알린다.
- 오류 문구는 해당 입력과 연결한다. 포커스가 있는 동안 오류가 생겨도 입력 내용을 지우지
  않는다.

## 완료 조건

- 이메일, Google과 Apple 로그인이 세션을 만든 뒤 프로필이 완성되지 않았으면 앱 화면
  대신 닉네임 화면을 연다.
- 프로필을 확인하는 동안 온보딩이나 홈 화면이 잠깐 나타나지 않는다.
- 두 값이 모두 저장된 세션을 복원하면 온보딩 없이 홈을 연다.
- 닉네임 화면에는 설명과 진행 표시가 없고, 아이디 화면에는 `@`와 고정 규칙 설명이 없다.
- 제공자 이름은 편집 가능한 닉네임 초기값으로, 이메일은 정규화된 아이디 초기 후보로
  나타난다.
- 아이디 입력을 멈추면 자동으로 사용 가능 여부를 확인한다. 중복이면 사용 가능한 후보
  세 개를 보여 주고 후보 선택 뒤 다시 확인한다.
- 아이디가 비었거나 형식 오류, 확인 중, 중복 또는 예약 상태면 `시작하기`가 비활성화된다.
- 아이디 화면에서 뒤로 갔다 돌아오면 두 입력값이 유지된다. 앱을 새로 열면 닉네임
  화면부터 다시 시작한다.
- 최종 저장은 두 값을 함께 반영한다. 중복 경쟁이나 네트워크 오류가 나면 값을 잃지 않고
  아이디 화면에서 복구한다.
- 프로필을 완성하면 홈을 열고, 앱을 다시 시작해도 온보딩을 반복하지 않는다.
- 데이터베이스 테스트는 닉네임 길이, 아이디 형식, 소문자 저장, 대소문자 비구분 고유성,
  예약어, RLS와 최종 저장의 원자성을 검증한다.
- 순수 함수 테스트는 이메일 후보 변환, 직접 입력 정규화와 숫자 후보 생성을 검증한다.
- React Native Testing Library 테스트는 진입 보호, 두 화면 이동, 뒤로가기 상태 보존,
  자동 확인, 후보 선택, 버튼 활성화와 오류 복구를 사용자 관점에서 검증한다.
- 로컬 Supabase 통합 테스트는 이메일 가입, 프로필 미완성 판정, 사용 가능 확인, 최종 저장과
  중복 경쟁을 실제 RLS 경로에서 검증한다.
- `agent-device`는 `auth:otp`와 함께 로그인, 두 온보딩 화면, 홈 진입과 앱 재시작 뒤 홈 복원을
  한 세션에서 검증한다.
- `supabase db reset`, 데이터베이스 타입 생성, 데이터베이스 테스트, Supabase 보안 검사,
  `bun run check`, `bun run check-types`와 `bun run test`가 통과한다.

## 가정

- 현재 운영 사용자와 보존해야 할 프로필 값이 없다. 구현 전에 데이터가 생기면 30자를
  넘는 닉네임과 새 예약어 충돌을 먼저 확인한다.
- 닉네임 길이는 PostgreSQL `length`와 같은 문자 단위로 판정한다. 여러 코드 포인트로 된
  이모지는 보이는 한 글자보다 길게 계산될 수 있다.
- 실시간 중복 확인의 지연 시간과 자동 재시도 횟수는 테스트에서 안정적으로 관찰할 수 있는
  범위 안에서 구현 시 정한다.

## 이번 구현에서 제외할 범위

- 온보딩 뒤 닉네임과 아이디를 바꾸는 설정 화면
- 아이디 검색, 멘션, 공개 프로필 주소와 이전 아이디 전달
- `@`가 붙은 아이디 표현
- 프로필 이미지, 소개, 역할과 프로필 탐색
- 기존 사용자 백필, 전환 안내와 단계적 출시
- 아이디 후보를 사용자가 새로 생성하는 별도 동작
- 온보딩 진행률 저장과 서버 임시 초안

## 남은 위험

- 실시간 사용 가능 확인은 아이디 존재 여부를 반복해서 추측하는 통로가 될 수 있다. 공개
  검색 기능이 생기기 전에도 과도한 호출이 관찰되면 요청 제한을 추가한다.
- 아이디 변경을 허용할 예정이지만 변경 주기와 이전 아이디 보호는 정하지 않았다. 공개
  주소나 멘션을 추가하기 전에 반드시 다시 결정한다.
- 파생 프로젝트의 서비스명이 템플릿 단계에서는 정해지지 않는다. 실제 사용자를 받기 전에
  서비스명과 운영 계정용 예약어를 보완해야 한다.
