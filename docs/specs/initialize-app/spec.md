# 앱 초기화 Skill 명세

## 목표

`initialize-app` Skill은 사용자가 이 템플릿으로 새 앱을 시작할 때 앱의
한 줄 설명과 원하는 시각적 특징을 받고, 테마를 정한 뒤 프로젝트 이름과
식별자를 설정한다.

새 CLI나 설정 스크립트를 만들지 않는다. 대화와 작업 순서는 `initialize-app`이 이끌고,
테마 생성은 `create-design-system`에, 프로젝트 식별자 적용은 `bun run setup`에
맡긴다. 기본 초기화가 완료된 뒤에는 사용자가 원할 때만 같은 대화에서
`create-app-assets`를 이어서 실행한다.

각 하위 작업은 자신이 적용하는 결정 계약과 승인 규칙을 그대로 따른다.
`initialize-app`은 그 규칙을 복사하거나 약화하지 않는다.

## Skill 구성

첫 버전은 다음 파일만 추가한다.

```text
.agents/skills/initialize-app/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── evals/
    ├── evals.json
    └── trigger-evals.json

.claude/skills/initialize-app
    → ../../.agents/skills/initialize-app
```

- `.agents/skills/initialize-app/SKILL.md`를 공용 원본으로 두고 Claude는 상대 경로
  심볼릭 링크로 같은 파일을 읽는다.
- Skill은 명시적으로 새 앱 초기화를 요청할 때만 시작한다. 이름만 바꾸거나,
  기존 앱의 테마만 바꾸거나, 앱 아이콘만 만드는 요청에는 실행하지 않는다.
- 첫 버전에는 새 `scripts/`, `references/`, `assets/`를 추가하지 않는다. 정확한 변경은
  기존 스크립트와 전용 Skill을 재사용한다.

## 시작 조건

사용자는 다음처럼 시작할 수 있다.

```text
$initialize-app 이 템플릿으로 새 앱을 시작하고 싶어.
```

요청을 받으면 먼저 다음 상태를 저장소에서 확인한다.

- `docs/app-brief.md` 유무와 내용
- `apps/mobile/global.css`의 현재 테마
- 테마 브리지와 렌더러 연결 상태
- `scripts/setup/identity.ts`가 소유하는 모든 식별자 필드
- 현재 Expo 앱 에셋과 설정 경로
- 관련 결정 계약과 작업 트리 상태

저장소에서 알 수 있는 값은 사용자에게 다시 묻지 않는다. 사용자의 설명과 현재
설정이 충돌하면 코드를 의도로 간주하지 말고 차이를 보여 준 뒤 의도를 확인한다.

## 입력

### 필수 입력

1. 앱이 누구를 위해 어떤 일을 하는지 적은 한두 문장
2. 테마에서 드러나길 원하는 시각적 특징을 적은 한 문장

앱 설명은 대상과 주요 일을 알 수 있어야 한다. 시각적 특징은 색상만이 아니라
대비, 온도, 모서리, 밀도와 분위기같이 결과를 판단할 수 있는 특징을 포함한다.

### 선택 입력

- 참고 이미지 또는 URL
- 피하고 싶은 색, 분위기, 형태나 상징

선택 입력이 없다는 이유로 테마 생성을 막지 않는다. 사용자가 글로만 설명하면
`create-design-system`의 글 입력 흐름을 따른다.

## 최소 대화

- 사용자가 필수 입력을 충분히 제공했으면 제품 범위나 데이터를 추가로 묻지 않고
  테마 단계로 간다.
- 테마를 정할 수 없는 정보 하나만 한 번에 묻는다. 답변으로 그 빈칸을 채웠으면
  다음 빈칸으로 넘어간다.
- 사용자가 만들 앱의 방향을 전혀 정하지 못했다면 초기화를 억지로 계속하지 않는다.
  제품 탐색은 기본 초기화의 범위가 아니며, 사용자가 원할 때만 `discover-opportunity`
  작업으로 따로 진행한다.
- 인터뷰 중에 첫 버전 범위, 핵심 사용자 흐름, 데이터 소유권, 로그인, AI, 결제,
  알림과 외부 서비스를 필수 항목으로 확인하지 않는다.

## 테마 생성과 적용

1. 앱 설명, 시각적 특징과 선택 입력을 `create-design-system`에 넘긴다.
2. `create-design-system`이 현재 스택과 결정 계약을 확인하고 후보를 만들도록 한다.
3. 사용자가 선택한 방향을 같은 미리보기에서 수정하고 명시적으로 적용을 승인할 때까지
   기다린다.
4. 후보 선택을 테마 적용 승인으로 간주하지 않는다.
5. 승인한 테마가 공식 `global.css`와 필요한 공통 연결 지점에 적용되고 관련 검증을
   통과하기 전에는 식별자 설정으로 넘어가지 않는다.

사용자가 테마 후보를 모두 거절하거나 적용을 취소하면 활성 테마를 바꾸지 않고 초기화를
멈춘다.

## 앱 요약 보존

테마가 적용되면 `docs/app-brief.md`를 만들거나 갱신한다. 문서는 확정한 내용만
짧게 보존하고 대화 기록, 후보 비교, 생성 이유, 토큰과 구현 방법을 넣지 않는다.

```md
# 앱 요약

## 한 줄 설명

{앱의 대상과 주요 일을 포함한 한 문장}

## 시각적 방향

{승인한 테마의 핵심 특징을 적은 한두 문장}

## 피할 표현

{사용자가 확정한 제약}
```

- 피할 표현이 없으면 해당 섹션을 생략한다.
- 기존 `docs/app-brief.md`의 확정 내용과 새 답변이 충돌하면 덮어쓰기 전에 차이를
  보여 준 뒤 사용자의 의도를 확인한다.
- 앱 요약을 저장하지 못하면 기본 초기화를 완료하지 않고 해결한 뒤 식별자
  설정으로 넘어간다.

## 프로젝트 정보 설정

테마 적용과 앱 요약 보존이 끝난 뒤 다음 값을 한 단계씩 정한다.

1. 앱 표시 이름
2. 영문 소문자 kebab-case 프로젝트 슬러그
3. iOS와 Android가 같이 쓸 완성된 reverse-DNS 모바일 앱 식별자

Skill은 앱 표시 이름에서 프로젝트 슬러그 후보를 만들 수 있지만 사용자가 확인한
값만 사용한다. 모바일 앱 식별자는 조직과 제품을 포함한 완성된 값을 받고 임의로
조직 영역을 만들지 않는다.

사용자가 세 값을 확인하면 Skill이 바꾸려는 필드와 값을 먼저 보여 준다. 같은 내용에
대한 명시적 확인을 받은 뒤에만 다음 명령을 실행한다.

```bash
bun run setup --project-slug <slug> --display-name "<name>" --mobile-app-id <id> --yes
```

- `--yes`는 Skill이 같은 값과 변경 필드를 대화에서 먼저 보여 주고 사용자의 명시적
  확인을 받았을 때만 사용한다.
- 이미 설정이 끝난 저장소에서 `--force`를 임의로 사용하지 않는다. 현재 값과 변경할 값을
  보여 준 뒤 사용자가 재설정을 명시적으로 요청할 때만 `--force`를 사용한다.
- `bun run setup`이 실패하면 테마와 `docs/app-brief.md`는 그대로 두고 기본 초기화를
  완료했다고 보고하지 않는다.

## 기본 초기화 검증

`bun run setup`이 성공하면 `scripts/setup/identity.ts`의 소유 목록을 기준으로 다음 값을
실제 파일에서 다시 읽어 확인한다.

- 루트 `package.json`의 `name`
- Expo `name`, `slug`와 `scheme`
- iOS `bundleIdentifier`
- Android `package`
- Supabase `project_id`
- `docs/app-brief.md`의 한 줄 설명과 시각적 방향

검증한 모든 값이 확정한 입력과 일치하고, `create-design-system`이 요구하는 테마 검증을
통과한 상태에서만 기본 초기화가 완료됐다고 보고한다.

## 선택형 앱 에셋 연결

기본 초기화가 완료되면 같은 대화에서 다음 한 가지만 묻는다.

```text
앱 아이콘과 스플래시도 지금 이어서 만들까요?
```

- 사용자가 동의하면 이 답변을 `create-app-assets`를 시작하는 명시적 요청으로 본다.
- 앱 요약, 승인한 테마와 기존 참고 자료를 같은 대화 맥락으로 이어 준다.
- `create-app-assets`는 시작 조건과 시안 선택, 최종 승인 및 플랫폼 검증을 독립적으로
  다시 확인한다.
- 사용자가 건너뛰거나 에셋 생성이 실패해도 기본 초기화 완료 상태를 취소하지 않는다.
- 사용자가 건너뛰면 다시 앱 에셋 생성을 권하지 않고 완료한다.

## 중단과 재실행

Skill은 별도 세션 파일이나 대화 상태 기계를 만들지 않는다. 재실행할 때 현재 파일에서
다음 진행 지점을 복원한다.

- 테마가 적용되고 `docs/app-brief.md`가 있지만 식별자가 템플릿 기본값이면 프로젝트 정보
  설정부터 재개한다.
- 식별자는 설정됐지만 테마 승인 내용을 확인할 수 없으면 현재 테마를 유지할지
  다시 만들지 하나만 확인한다.
- 테마, 앱 요약과 식별자가 모두 일치하면 이미 기본 초기화가 완료됐음을 보고하고
  해당 파일을 다시 바꾸지 않는다.
- 이미 설정한 이름과 식별자를 재설정하지 않는다. 사용자가 재설정을 요청할 때만
  현재 값과 새 값을 비교하고 `--force`를 사용한다.
- 저장소 상태만으로 확신할 수 없는 승인은 임의로 생성하지 않는다. 변경을 다시 적용할 필요가
  있을 때만 사용자의 의도를 확인한다.

## 실패와 복구

- 필수 입력이 부족하면 파일을 바꾸지 않고 테마에 필요한 정보 하나만 묻는다.
- 테마 후보가 모두 거절되거나 적용 승인을 받지 못하면 테마와 식별자를 바꾸지 않고
  멈춘다.
- 테마 적용 또는 검증이 실패하면 식별자 설정으로 넘어가지 않는다.
- `docs/app-brief.md` 작성이 실패하면 식별자 설정으로 넘어가지 않는다.
- `bun run setup`이 취소되거나 실패하면 테마와 앱 요약을 그대로 보존하고 실패한 입력과
  명령을 보고한다. 기본 초기화는 미완료 상태다.
- 선택한 앱 에셋 생성이 실패하거나 중단되면 기본 초기화 완료 상태를 유지하고,
  `create-app-assets`의 현재 활성 에셋과 후보 상태를 따로 보고한다.
- 관련 파일에 사용자 변경이 있어 안전하게 이어쓸 수 없으면 덮어쓰지 말고 충돌하는
  파일과 필요한 선택을 알린다.

## 완료 조건

- `.agents/skills/initialize-app/SKILL.md`와 유효한 `agents/openai.yaml`이 있다.
- `.claude/skills/initialize-app`이 공용 Skill 원본을 가리킨다.
- Skill은 앱 설명과 시각적 특징이 충분하면 광범위한 제품 질문 없이 테마 단계로
  간다.
- 명시적 승인 전에는 공식 테마 원본, 식별자와 활성 앱 에셋을 바꾸지 않는다.
- 기본 초기화는 승인한 테마 적용, `docs/app-brief.md` 보존, `bun run setup` 성공과
  식별자 검증을 모두 통과해야 완료된다.
- 앱 에셋을 건너뛰어도 기본 초기화 완료 상태는 유지된다.
- 재실행할 때 완료한 단계를 다시 적용하거나 사용자 승인을 임의로 생성하지 않는다.
- 제품 기능, 화면, 데이터, 인증, AI, 결제, 알림과 외부 서비스를 만들거나 설정하지
  않는다.

## 검증 시나리오

Skill 구현은 최소한 다음 행동을 포함한 평가를 통과해야 한다.

1. 앱 설명과 참고 URL이 충분하면 제품 범위를 묻지 않고 `create-design-system`으로 간다.
2. 사용자가 글로만 시각적 특징을 주면 `create-design-system`이 제안하는 방향 선택부터
   진행한다.
3. 사용자가 앱이 하는 일을 정하지 못했으면 광범위한 제품 인터뷰를 시작하지 않고
   초기화를 멈춘다.
4. 테마 후보만 고른 상태에서 공식 테마 원본과 식별자를 바꾸지 않는다.
5. 테마를 적용한 뒤 `docs/app-brief.md`를 보존하고, 확정한 세 식별자 입력만 `bun run setup`에
   넘긴다.
6. 기본 초기화가 끝난 뒤 앱 에셋을 건너뛰면 초기화를 미완료로 되돌리지 않는다.
7. 사용자가 앱 에셋 생성을 선택하면 같은 대화에서 `create-app-assets`로 이어지지만
   시안 선택과 최종 승인을 자동으로 간주하지 않는다.
8. 테마만 적용된 중간 상태에서 재실행하면 이미 완료한 테마 작업을 반복하지 않고
   프로젝트 정보 설정부터 재개한다.
9. 이미 완료한 저장소에서 재실행하면 파일을 다시 바꾸거나 `--force`를 임의로 사용하지 않는다.

## 가정

- 대상 저장소는 Expo, HeroUI Native와 Uniwind를 사용하는 이 템플릿 또는 그 파생 앱이다.
- 사용자는 테마 후보와 필요한 앱 에셋을 시각적으로 판단할 수 있다.
- 앱 초기화는 사람과 대화하는 작업이며 무인 CI 실행을 요구하지 않는다.
- `docs/app-brief.md`는 후속 테마와 앱 에셋 작업이 다시 읽을 수 있는 짧은 앱 맥락이다.

## 이번 범위에서 제외할 기능

- 독립 실행형 CLI와 대화형 터미널 UI
- 별도 모델 연결, 인증, 텔레메트리와 세션 상태 파일
- 범용 제품 발견, 시장 조사와 사업 모델 설계
- 첫 버전 기능, 사용자 흐름, 화면과 데이터 명세
- 로그인, AI, 결제, 알림, 분석과 외부 서비스 설정
- 새 테마 생성 규칙, 식별자 치환 규칙과 앱 에셋 생성 규칙의 중복
- App Store·Google Play 스크린샷, feature graphic과 배포

## 남은 위험

- 저장소 파일만으로 이전 테마 적용의 명시적 승인 여부를 완전히 증명할 수는 없다.
  재실행 중 새 변경이 필요할 때는 현재 테마를 유지할지 사용자에게 확인해야 한다.
- 테마를 먼저 적용한 뒤 식별자 설정이 실패하면 저장소는 중간 상태에 남는다. `docs/app-brief.md`와
  실제 설정을 읽어 식별자 설정부터 재개해야 한다.
- 동일한 설명으로 만든 HTML 테마 미리보기와 실제 React Native 화면은 픽셀 단위로 같지 않다.
  `create-design-system`의 실제 기기 검증 규칙을 그대로 적용해야 한다.
