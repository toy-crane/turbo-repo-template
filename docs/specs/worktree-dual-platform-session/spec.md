# 한 worktree에서 두 플랫폼 함께 검증

## 사용자에게 보이는 결과

- 한 worktree에서 iOS Simulator와 Android Emulator를 함께 띄워 두고, 같은 변경을 두 기기에서 나란히 확인한다.
- `bun run dev ios`를 실행한 뒤 `bun run dev android`를 실행하면 iOS 세션이 살아 있는 채로 Android가 더해진다. 먼저 띄운 플랫폼이 내려가지 않는다.
- 플랫폼을 바꿀 때마다 API와 Metro가 다시 시작되고 Android 네이티브 빌드를 처음부터 기다리는 일이 사라진다.
- 세션이 API와 Metro를 다시 시작할 때, 명령에 적지 않은 플랫폼의 앱도 새 Metro에 다시 붙는다. 명령이 끝나면 두 기기가 모두 검증할 수 있는 상태다.

## 승인한 범위

- 한 worktree에서 iOS와 Android 개발 세션을 동시에 유지한다.
- 플랫폼 시작 명령을 누적 방식으로 바꾼다. 새 플랫폼을 시작해도 이미 돌고 있는 플랫폼을 내리지 않는다.
- 두 플랫폼이 같은 개발 세션 주소를 사용하게 만든다.
- API·Metro 재시작 뒤 붙어 있던 모든 플랫폼의 앱을 다시 연결한다.
- 세션 종료와 자원 정리 명령이 두 플랫폼을 함께 다룬다.
- 결정 계약 [Worktree 개발 세션](../../decisions/worktree-development-sessions.md)에서 이 명세와 어긋나는 조항, 재검토 조건, 제외한 대안을 갱신한다.

## 관찰 가능한 인수 기준

1. iOS 세션이 돌고 있는 worktree에서 `bun run dev android`를 실행하면, 명령이 끝난 시점에 iOS Simulator의 앱과 Android Emulator의 앱이 모두 이 worktree의 Metro에 붙어 있다.
2. 두 플랫폼이 붙어 있는 동안 두 기기 모두에서 API 요청이 성공하고 이메일 코드 로그인을 끝까지 진행할 수 있다.
3. Metro 입력이나 개발 세션 환경을 바꾼 뒤 한 플랫폼만 지정해 다시 실행하면, 명령이 끝난 시점에 두 기기의 앱이 모두 새 Metro에 다시 붙어 있다.
4. 두 플랫폼이 붙어 있어도 이 worktree가 사용하는 Metro 포트는 하나, API 포트는 하나다.
5. `bun run dev:stop`은 두 플랫폼의 기기와 이 worktree의 API·Metro를 함께 멈춘다. slot, 기기 배정, 앱 데이터는 남는다.
6. `bun run dev:remove`는 두 플랫폼의 기기를 모두 초기화해 풀로 돌려놓고 slot을 반납한다.
7. Android 도구가 없는 컴퓨터에서 `bun run dev android`가 실패해도 이미 돌고 있던 iOS 세션과 기기는 그대로 살아 있다.
8. 두 플랫폼을 함께 띄운 worktree 옆에서 다른 worktree가 자기 세션을 시작해도 서로의 포트, 기기, 앱 데이터를 침범하지 않는다.

## 정해진 제약과 이유

- **앱은 두 플랫폼에서 같은 개발 세션 주소를 본다.** 지금은 iOS에 `127.0.0.1`, Android에 `10.0.2.2`를 넣고 이 값이 번들에 박히기 때문에, Metro 프로세스 하나가 한 플랫폼의 주소만 담을 수 있었다. 이 차이가 "한 번에 한 플랫폼" 제약의 뿌리다. 주소를 하나로 맞춰야 Metro 하나가 두 플랫폼 번들을 함께 내보낸다.
- **worktree 하나는 slot 하나만 쓴다.** 플랫폼마다 Metro를 따로 띄우면 주소 차이를 그대로 두고도 동시 실행이 되지만, 메모리와 변환 캐시가 두 배가 되고 포트와 상태 관리가 늘어난다. 하나의 Metro가 두 플랫폼을 서빙하는 편을 택한다.
- **플랫폼 인수는 계속 필수다.** 기존 결정을 유지한다. 실행 대상을 명령에서 확인할 수 없게 만들지 않는다.
- **기기는 플랫폼별로 하나씩 독점 배정하고 앱 데이터를 유지한다.** 두 플랫폼이 동시에 돌면 한 worktree가 iOS 기기 하나와 Android 기기 하나를 함께 점유한다.
- **네이티브 Development Build는 지금처럼 플랫폼과 native fingerprint를 기준으로 저장소 전체에서 공유한다.**

## 가정

뒤집어도 되는 판단이며, 어긋나면 이 명세를 고친다.

- `dev:stop`과 `dev:remove`는 플랫폼 인수를 받지 않고 이 worktree의 두 플랫폼을 함께 다룬다.
- 한 플랫폼만 실행했고 다른 플랫폼이 돌고 있지 않으면 지금과 똑같이 동작한다.
- 두 번째 플랫폼을 시작하다 실패해도 먼저 돌던 플랫폼의 프로세스와 기기는 건드리지 않는다.
- 주소를 통일해도 native fingerprint는 바뀌지 않아 이미 만들어 둔 공용 빌드를 그대로 쓴다. 결정 계약에 `EXPO_PUBLIC_API_URL`만 바꾼 fingerprint가 모두 같았다는 근거가 남아 있다.
- 두 플랫폼이 붙어 있어도 API 프로세스는 하나면 충분하다. API는 모바일 공개 환경 변수를 읽지 않는다.

## 손대지 않는 곳

- **로컬 Supabase 스택의 공유 방식.** 모든 worktree가 함께 쓰는 현재 구조를 그대로 둔다. 이번 변경은 앱이 그 스택에 닿는 주소만 다룬다.
- **Metro 캐시 자동 초기화 규칙과 worktree별 Gradle 홈.** 각각 별도 근거로 정한 격리 장치이며 플랫폼 동시 실행과 무관하다.
- **앱이 개발 세션 주소를 읽는 방식.** `EXPO_PUBLIC_DEV_SESSION_API_URL`과 `EXPO_PUBLIC_DEV_SESSION_SUPABASE_URL`이라는 이름과 우선순위는 유지한다. 값만 바뀐다.
- **Expo Web, 실제 기기, 원격 기기, CI 기기.** 결정 계약이 이미 범위 밖으로 둔 영역이다.

## 미룬 것

- 한 줄로 두 플랫폼을 함께 띄우는 편의 명령. 누적 실행으로 목적을 달성한 뒤 필요가 확인되면 다시 본다.
- 플랫폼 하나에 기기를 여러 대 붙이거나 기기를 세 대 이상 동시에 쓰는 경우.
- 지금 어떤 플랫폼이 돌고 있는지 보여 주는 조회 명령.

## 남은 위험

- Android Emulator가 호스트의 API와 Supabase에 닿는 경로가 끊기면(에뮬레이터 재시작, adb 서버 재시작) 앱이 서버에 붙지 못한다. 지금도 Metro 포트가 같은 종류의 경로에 기대고 있어 위험의 성격은 같지만, 끊겼을 때 영향을 받는 대상이 늘어난다.
- 재시작할 때 두 플랫폼 앱을 모두 다시 여는 동작은, 한 플랫폼만 지정한 명령이 다른 기기의 앱도 종료하고 다시 연다는 뜻이다. 그 기기에서 손으로 만들어 둔 화면 상태는 사라진다.
- 두 기기를 함께 띄우면 메모리와 CPU 사용이 늘어난다. 느린 컴퓨터에서는 두 앱의 첫 번들이 지금보다 오래 걸릴 수 있다.
- 기기 풀에서 한 worktree가 두 대를 동시에 점유하므로, worktree 수가 많은 컴퓨터에서 기기와 자원이 더 빨리 늘어난다.
